# 网站与维护流程评估

评估日期：2026-11-07。依据本地 app.js / app.css、构建、导入、目录和 MCP 源码及现有 Markdown；本轮未进行浏览器视觉、性能或线上可用性测试。以下区分已确认实现、源码问题与建议，不给未经实测的视觉评分。

## 判断

作为「可预览、可定制、可导出的设计库」已有扎实基础；作为长期收集工作台，缺少从待整理到可复用的清楚状态与管理入口。下一步应优先提高收集成功率、找回效率和质量可信度，暂不追求更多模板数量。

## 已做得好的部分

- Website / Graphic 分区清楚，共用色板，内容文件不必为展示结构搬迁。
- 模板、效果、转场的颗粒度分开，可以整站或局部复用。
- 预览、参数调整、整站导出与本地 MCP 连接起来，超过单纯截图收藏。
- 已有行业场景快捷入口、筛选 URL 持久化、搜索同义词、空结果跨类别提示和 My list，不需要重做一套相同功能。
- 静态缩略图与按需详情加载方向合理；有触屏和 reduced-motion 约束。

## 核心流程建议

对使用者：选用途 → 搜索/筛选 → 查看用途与限制 → 预览 → 加入项目清单 → 复制/下载/交给 AI。

对维护者：收进 Inbox → 确认来源与许可 → 去重与分类 → 补使用说明 → 验收 → Ready / Needs work / Archived。

后者目前主要依赖本地命令与人的记忆。可以先用文档和命令行建立流程，再决定是否需要登录后的管理界面；不要一开始把原始文件上传入口放到公开前台。

## P0：先修会误导或影响公开边界的问题

| 发现 | 源码依据 / 影响 | 建议与验收 |
|---|---|---|
| 模板及 Graphic 的 catalog license 被写成固定「库内自有」 | `build/catalog.py` 的模板 / Graphic items；导入来源可能被错误表述 | 保留真实许可与 source，另设可见性；受限测试条目不出现在公共目录/包，公开 imported 条目不被标成自制 |
| 页面隐藏不能代替发布文件审计 | 构建有多处排除 local_only，但转场、效果和预览复制路径并非统一检查 | 核对每类的许可支持；建立 public manifest / 实际文件 / ZIP 交叉检查，发现残留就失败 |
| 维护文档互相矛盾 | README 数量、旧 API、build 清理行为、静态 fallback 等已过期 | 本轮已拆分并修正文档；长期让数量来自生成目录，关键行为说明跟随源码更新 |
| 未来连 GitHub 时需要单独核对本地文件 | `.gitignore` 当前未排除 `_work/`，library 也可能含 local_only；构建过滤不等于 Git 自动排除 | 首次提交前按实际路径核对受限素材与暂存清单；不要只凭 public_html 已忽略就提交整棵目录 |

这里的目录许可标注问题不等于已经证实发生受限资源泄漏；需要实际构建与文件检查才能确认。

| 需求 | 当前情况 | 建议与验收 |

## P2：规模扩大后再做

- 比较 2–3 个模板/效果：构图、支持能力、依赖、最近检查和用途，不仅比较截图。
- Related items 与变体关系：按机制、场景、style / taxonomy 推荐；保留稳定 ID，不为改名字破坏引用。
- 一个只读 `check_library` 命令：schema、taxonomy、重复 slug、order 孤儿、缺文件、坏链接、说明完整性、许可输出一致性。命令退出成功需代表所有硬性项目通过。
- UI 浏览器回归：搜索 → 筛选 → 详情 → 返回保留状态；手机筛选开关、键盘焦点、下载与复制失败提示。现有 mobile_audit 不覆盖这些。
- 用真实数据测首屏加载、iframe 回退数量、内存和慢网；没有测量前不引入新框架或虚拟列表。

## 建议的最小元数据演进

现有字段和许可值保持兼容，逐步增加：source_url、author、added_at、updated_at、status、tested_at、dependencies、supports_touch、supports_reduced_motion、related_ids、notes。

这是建议 schema，不是当前已经支持的功能。状态可先用 inbox / needs-work / ready / archived；status 管质量，visibility 管公开范围，license 保留权利依据。不要用单个 local_only 同时承担三种含义。迁移时明确未知值，不凭空补检查日期与许可。
